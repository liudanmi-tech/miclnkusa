# 对话式交互方案 0613

> 状态：方案已确认，待实施
> 日期：2026-06-13

---

## 一、背景与目标

### 现有问题
- 用户录音后需等待约 3 分钟异步处理（转录→技能匹配→生图）
- 处理完成后 Moment 卡片才可点击，进入 detail 页才看到技能
- 从录音到用户真正得到 AI 反馈，路径太长，用户放弃率高

### 目标
- 录音按钮点击后立即进入对话，0 等待时间
- 用户像使用豆包一样，逐条发消息，AI 实时回复
- 退出时可选择将对话内容生成场景图片，形成 Moment 封面

---

## 二、新旧流程对比

### 旧流程
```
点录音按钮
  → 录音（按住/松开）
  → 上传音频
  → 服务端：转录 → 情绪分析 → 场景分类 → 技能匹配 → 生图
  → 客户端轮询 3 分钟
  → Moment 卡片变可点击
  → 进入 detail 页看技能卡
  → 点技能卡 → AI Assistant 页面
```

### 新流程（方案B：完全替换）
```
点录音按钮
  → POST /assistant/init-chat-session
  → 拿到 session_id
  → 立即进入 ChatAIAssistantView（全屏）

用户对话中：
  → 默认语音输入（SFSpeechRecognizer 转文字），可切换文字输入
  → 第1条消息发出后，服务端后台做轻量技能匹配
  → AI 回复带技能标签（内联展示，非 tab）
  → 后续每轮：技能 context + KG 记忆 → Gemini 生成回复

退出时弹窗：
  ┌─────────────────────────────────┐
  │  "对话转图片"                    │  → 生图（用 Moment 已选风格）→ 封面=生成图 → 点击=detail页
  │  "直接退出"                      │  → 封面=用户 emoji style 情绪头像 → 点击=重入对话
  └─────────────────────────────────┘
```

### 3.2 阶段二-A：第一条消息（主线 + 后台并行）

**触发**：用户发出第一条消息（history 为空，strategy_analysis 不存在）

```
[iOS] POST /api/v1/assistant/chat   (Accept: text/event-stream)
    Body:
    {
      "session_id":        "550e8400-...",
      "skill_id":          "emotion_recognition",  ← 固定初始值
      "message":           "今天开会被领导当众批评了",
      "history":           [],                     ← 第1条时为空
      "is_chat_session":   true,
      "skill_mode":        "auto",
      "image_base64_list": null
    }
```

#### [主线路径 — 立即执行，不等任何技能匹配]

```
Step 1. 查询 strategy_analysis
    SELECT id FROM strategy_analysis WHERE session_id = "550e8400-..."
    → 0 rows（新 chat session）
    → 使用默认 skill_id = "emotion_recognition"
    → skill_content = get_skill_config("emotion_recognition")
                        .strategy_content       ← ~600 tokens

Step 2. KG 记忆检索（asyncio.wait_for，timeout=3.0s）
    get_ai_context_kg(message="今天开会被领导当众批评了", user_id)
    ├─ SELECT * FROM kg_persons
    │  WHERE user_id=? ORDER BY mention_count DESC LIMIT 20
    │  → 关键词匹配 message 中出现的人名
    └─ 返回:
         memory_ctx  : "记忆中：上司王经理曾两次公开批评..."（或空字符串）
         memory_used : true / false

Step 3. Prompt 组装
    ┌─ system ──────────────────────────────────────┐
    │  {skill_content}              ~600 tokens     │
    │  {memory_ctx}                 ~0-200 tokens   │
    └───────────────────────────────────────────────┘
    ┌─ history ─────────────────────────────────────┐
    │  (空)                                         │
    └───────────────────────────────────────────────┘
    ┌─ user ────────────────────────────────────────┐
    │  "今天开会被领导当众批评了"    ~10 tokens      │
    └───────────────────────────────────────────────┘
    总 prompt tokens：~610-810

Step 4. Gemini 2.5-flash 流式生成 → SSE 逐事件推送
```

**SSE 时间轴（第1条消息）**：

```
t=0ms        建立连接

t≈10ms       { "type": "meta",
               "skill_id": "emotion_recognition",
               "skill_name": "情绪识别",
               "memory_used": true,
               "mood_state": "Frustrated" }
               // mood_state = 当前轮 AI 对这条消息的情绪推断（非最终值）
               // iOS 用途①：驱动对话中的 UI 动效（如背景渐变、emoji 动画）
               // iOS 用途②：覆写 viewModel.lastMoodState（退出时作为 Moment 卡片占位）
               // ⚠️ 每轮都会更新，最终由 _async_session_finalize 生成权威值写入 DB

t≈350ms      { "type": "token", "content": "我" }  ← TTFT（目标 <500ms）
t≈360ms      { "type": "token", "content": "听到你" }
             ...（约 150-200 次 token 事件）

t≈2500ms     { "type": "suggestions",
               "items": ["你当时怎么回应的？", "这不是第一次了吗？"] }

t≈2500ms     { "type": "done" }

t≈3000-5000ms（后台技能匹配完成后推送，SSE 若已关闭则丢弃）
             { "type": "skill_tags",
               "tags": ["情绪识别", "职场丛林法则"],
               "skill_ids": ["emotion_recognition", "workplace_jungle"] }
```

```
Step 5. 流结束后，fire-and-forget：
    asyncio.create_task(
      save_kg_from_chat(
        session_id = "550e8400-...",
        user_msg   = "今天开会被领导当众批评了",
        ai_msg     = "<完整 AI 回复文本>",
        user_id    = <user_id>
      )
    )
    → 异步写 KG，不阻塞任何响应
```

#### [后台路径 — asyncio.create_task，与主线完全并行]

```
_init_skill_matching(session_id, message, user_id, db)

Step 1. 构造 pseudo_transcript
    [{ "speaker": "Speaker_0",
       "text":    "今天开会被领导当众批评了",
       "is_me":   true }]

Step 2. 读用户技能偏好
    SELECT skill_id FROM user_skill_preferences
    WHERE user_id=? AND selected=true
    → 有记录 → selected_ids = [用户已选 N 个技能 ID]
    → 无记录 → selected_ids = [全部 43 个系统技能 ID]（fallback）

Step 3. classify_and_score(pseudo_transcript, selected_ids)
    → 1次 Gemini Flash 调用（~1-2 秒）
    → prompt：Step0（他人类型识别）+ Step1（6类场景分类）+ Step2（技能打分 0-100）
    → 返回 JSON:
    {
      "other_person_type": "boss_or_superior",
      "primary_category":  "work_life",
      "scene_description": "用户在会议中被领导公开批评",
      "skill_scores": {
        "emotion_recognition": 88,
        "workplace_jungle":    82,
        "nonviolent_comm":     71,
        "depression_prev":     45,
        ...
      }
    }

Step 4. _build_stubs_auto(selected_ids, scores, "work_life")
    过滤规则（chat session 门槛 score ≥ 75，比 review session 的 ≥90 低）：
    → emotion_recognition: 88 ✓
    → workplace_jungle:    82 ✓
    → nonviolent_comm:     71 ✗（低于 75）
    → depression_prev:     45 ✗
    每场景上限 3 个，primary_category 强制保留
    结果：
    [
      { skill_id: "emotion_recognition", name: "情绪识别",     score: 88 },
      { skill_id: "workplace_jungle",    name: "职场丛林法则", score: 82 }
    ]

Step 5. _append_always_run(stubs, pseudo_transcript)
    → emotion_recognition 置顶（已在 stubs 中，不重复添加）
    → 扫描危机关键词（"自残"/"想死"等）→ 未命中 → 不追加 depression_prevention

Step 6. DB 写入（UPSERT，防止网络重试导致 unique constraint 报错）
    INSERT INTO strategy_analysis (
      session_id        = "550e8400-...",
      user_id           = <user_id>,
      skill_cards       = [stubs] :: JSONB,
      scene_category    = "work_life",
      other_person_type = "boss_or_superior",
      created_at        = now()
    )
    ON CONFLICT (session_id) DO UPDATE SET
      skill_cards       = EXCLUDED.skill_cards,
      scene_category    = EXCLUDED.scene_category,
      other_person_type = EXCLUDED.other_person_type
    // 同一 session 重试时直接覆盖，不报错

Step 7. 推送 skill_tags SSE 事件
    → SSE 连接仍活跃 → 写入 response queue
    → SSE 已关闭    → 丢弃，记录 warning 日志
    // skill_tags 丢失时 iOS 有补偿机制，见下方
```

**iOS 侧 skill_tags 补偿机制（第1条消息后）：**

```
[iOS] SSE done 事件收到后
    │
    ├─ 检查：hasReceivedSkillTags == false？
    │
    ├─ 是（skill_tags 丢失）→ 延迟 500ms 后：
    │   GET /api/v1/tasks/sessions/{session_id}/strategy
    │   → 返回 strategy_analysis.skill_cards（后台匹配已写入 DB）
    │   → 从 skill_cards 中提取 skill_name 列表
    │   → 更新技能标签区（替换"分析中..."）
    │   → 失败（DB 还没写完）→ 再等 1s 重试 1 次，仍失败则保留"分析中..."
    │
    └─ 否（正常收到）→ 不做额外请求
```

```
    │  "我当时真的很崩溃，不知道怎么办"              │
    └───────────────────────────────────────────────┘

Step 5. 漂移检测（仅 skill_mode=="auto"，后台并行）

Step 6. Gemini 流式生成 + SSE 推送（同 3.2 Step 4）
    SSE 事件序列相同，通常无 skill_tags

```

#### 3.3.1 漂移检测（_detect_skill_drift）内部数据流

```
输入：message="我当时真的很崩溃"
      current_skill_id="emotion_recognition"
      session_id, user_id

Step A. 关键词快速扫描（<1ms，无 LLM）
    keyword_map = {
      "work_life":       ["老板","领导","KPI","绩效","同事","客户","开会"],
      "relationships":   ["男朋友","女朋友","分手","失恋","闺蜜","朋友"],
      "family":          ["妈妈","爸爸","孩子","老公","老婆","婆婆","亲戚"],
      "campus_life":     ["导师","同学","考试","宿舍","选课","毕业"],
      "personal_growth": ["迷茫","方向","我感觉","自我","成长"],
      "life_skills":     ["房东","医生","快递","邻居","合同","诊断"]
    }
    current_category = strategy_analysis.scene_category  // "work_life"
    detected_category = first_match(message, keyword_map) // None（无明显新分类关键词）
    → detected == None 或 == current_category → 结束，保持 emotion_recognition（最常见路径）
    → 不同分类 → 进入 Step B

Step B. classify_and_score（~1-2 秒，仅 Step A 命中时触发）
    → 同 3.2 后台 Step 3，返回新 top 技能及分数

Step C. 判断是否切换
    new_top_skill_id  = argmax(new_scores)
    new_top_score     = new_scores[new_top_skill_id]
    current_score     = new_scores.get(current_skill_id, 0)

    if new_top_skill_id != current_skill_id
       and new_top_score - current_score > 15:
      → UPDATE strategy_analysis SET skill_cards=[updated] WHERE session_id=?
      → 推送 SSE:
          { "type": "skill_drift",
            "new_skill_id":   "workplace_jungle",
            "new_skill_name": "职场丛林法则",
            "old_skill_id":   "emotion_recognition",
            "score_diff":     22 }
    else:
      → 保持当前技能（分差不足 15，防抖）
```

### 3.4 阶段三 A：退出 → 对话转图片

**触发**：用户点击 × → iOS 检测 `conversation.isEmpty == false` → ActionSheet 选"对话转图片"

```
[iOS]
Step 1. 读取 TaskListViewModel.selectedStyleKey  ← Moment 顶部当前风格
        示例值："ghibli"

Step 2. POST /api/v1/assistant/generate-image-from-chat
    Body:
    {
      "session_id": "550e8400-...",
      "conversation": [
        { "role": "user",      "content": "今天开会被领导当众批评了" },
        { "role": "assistant", "content": "我听到你今天承受了很大压力..." },
        { "role": "user",      "content": "我当时真的很崩溃" },
        { "role": "assistant", "content": "崩溃是正常的反应..." }
      ],
      "style_key": "ghibli"
    }

[服务端] generate_image_from_chat()

Step 1. 构造 synthetic_transcript（仅取用户消息，过滤 AI 回复）
    ⚠️ 只对 role=="user" 的消息转换，assistant 消息不进入生图管线
    ⚠️ 原因：若带入 AI 回复（is_me=false），generate_scene_images 会进入
           场景1（双人对话模式），把 AI 当作"对方"生成对话场景图 — 不符合需求
           只传用户消息 → 单说话人 → 自动进入场景2（旁白模式）→ 正确
    user 消息 → { text: content, is_me: true, speaker: "Speaker_0" }
    AI 消息   → 跳过，不加入 transcript
    结果（只含用户自己的话）：
    [
      { text: "今天开会被领导当众批评了",   is_me: true, speaker: "Speaker_0" },
      { text: "我当时真的很崩溃",            is_me: true, speaker: "Speaker_0" }
    ]

Step 2. 查 user profile_id
    SELECT id FROM profiles
    WHERE user_id=? AND relationship_type="自己" LIMIT 1
    → profile_id: UUID

Step 3. speaker_mapping = { "Speaker_0": profile_id }
    单说话人 Speaker_0 映射到用户自己的 profile
    → generate_scene_images 判断 speaker_count==1 且 profile.relationship_type=="自己"
    → 自动进入 is_narration_mode=True（场景2：用户旁白模式）
    → 无需改动 scene_image_generator.py，复用现有逻辑

Step 4. DB 更新
    UPDATE sessions SET
      image_status = "generating",
      status       = "processing"
    WHERE id = "550e8400-..."

Step 5. 异步触发生图
    asyncio.create_task(
      generate_scene_images(
        transcript      = synthetic_transcript,   ← 上面构造的
        session_id      = "550e8400-...",
        user_id         = <user_id>,
        style_key       = "ghibli",
        speaker_mapping = { "Speaker_0": profile_id },
        max_images      = 1
      )
    )
    内部流程：
      → Gemini：根据 transcript 生成图片场景 prompt
      → Imagen API：生成图片（约 10-30 秒）
      → R2 上传：sessions/{user_id}/550e8400/images/1.png
      → DB 更新：
          UPDATE sessions SET
            image_status    = "completed",
            cover_image_url = "https://r2.cdn/sessions/.../images/1.png",
            status          = "archived"
          WHERE id = "550e8400-..."

Step 6. 返回 202
    { "status": "generating", "session_id": "550e8400-..." }

[iOS] 收到 202
Step 1. 关闭 ChatAIAssistantView
Step 2. TaskItem 更新（预设状态）：
         status: .archived  coverType: "generated"（先 shimmer 等待）
Step 3. 启动图片状态轮询：
         GET /api/v1/tasks/sessions/550e8400-.../images/status
         每 3 秒，最多 60 次（3 分钟超时）
         → { image_status: "generating" }  → 继续轮询
         → { image_status: "completed",
              cover_image_url: "https://..." }
              → TaskItem.coverImageUrl = url
              → Moment 卡片封面切换为生成图
         → 超时（3分钟）→ 降级为 emoji 头像封面
```

### 3.5 阶段三 B：退出 → 直接退出

**触发**：用户点击 × → iOS 检测 `conversation.isEmpty == false` → ActionSheet 选"直接退出"

```

    Body:
    {
      "session_id":   "550e8400-...",
      "conversation": [
        { "role": "user",      "content": "今天开会被领导当众批评了" },

      status          = "archived",
      image_status    = "none",
      finalize_status = "pending"   ← 等待 _async_session_finalize 写完后变为 "completed"

[iOS] 收到 200

Step 2. TaskItem 立即更新为占位状态（finalize 还在后台跑）：

                          // 比固定 neutral 更准确，用户感知更自然

Step 4. 点击 Moment 卡片

         → fullScreenCover: ChatAIAssistantView(sessionId: "550e8400-...")
```

#### ② `POST /api/v1/assistant/chat`（已有，修改）
```
改动点：新增 is_chat_session 字段，当 true 时：
  - 允许 strategy_analysis 不存在（不 raise 404）
  - 第1条消息时后台触发轻量技能匹配
  - SSE 新增 skill_tags 事件类型

Request Body（新增字段）:
{
  "session_id": "uuid",
  "skill_id": "emotion_recognition",   // chat mode 下初始固定值，后续由 skill_tags 更新
  "message": "今天开会被领导当众批评了",
  "history": [...],
  "is_chat_session": true,             // 新增
  "image_base64_list": null
}

SSE 新增事件：
{ "type": "skill_tags", "tags": ["情绪识别", "职场丛林法则"] }

服务端新增逻辑：
  if is_chat_session and strategy_analysis 不存在 and len(history)==0:
    asyncio.create_task(_init_skill_matching(session_id, message, user_id, db))
```

#### ③ `POST /api/v1/assistant/generate-image-from-chat`
```
用途：将对话内容转为 synthetic transcript，触发现有生图管线
style_key 来源：iOS 端 Moment 顶部风格选择器当前选中值（TaskListViewModel.selectedStyleKey）

Request Body:
{
  "session_id": "uuid",
  "conversation": [
    { "role": "user",      "content": "今天开会被领导批评了" },
    { "role": "assistant", "content": "我注意到你今天承受了很大压力..." },
    ...
  ],
  "style_key": "ghibli"   // Moment 顶部风格选择器当前选中值
}

Response 202:
{ "status": "generating", "session_id": "uuid" }

服务端动作：
  1. 构造 synthetic_transcript（仅 role=="user" 消息，assistant 消息跳过）：
       [{ text: msg.content, is_me: True, speaker: "Speaker_0" }]
       ⚠️ AI 回复不入 transcript → 单说话人 → 生图进入场景2（旁白模式）
  2. 查询 user profile_id（relationship_type="自己"）
  3. speaker_mapping = {"Speaker_0": user_profile_id}
  4. asyncio.create_task(
       generate_scene_images(
         transcript=synthetic_transcript,
         session_id=session_id,
         user_id=user_id,
         style_key=style_key,
         speaker_mapping=speaker_mapping,
         max_images=1
       )
     )
  5. UPDATE sessions SET image_status="generating"
  6. RETURN 202
```

#### ④ `POST /api/v1/assistant/close-chat-session`
```
用途：直接退出时归档 session（不生图），并触发异步后处理

Request Body:
{
  "session_id": "uuid",
  "conversation": [
    { "role": "user",      "content": "..." },
    { "role": "assistant", "content": "..." }
  ]
}
// conversation：iOS 本地持有的完整对话，供服务端 _async_session_finalize 生成
// card_title / summary / mood_state 使用，不在 body 里单独传 mood_state

Response 200:
{ "status": "archived" }

服务端动作：
  1. UPDATE sessions SET status="archived", image_status="none", finalize_status="pending"
  2. asyncio.create_task(_async_session_finalize(session_id, conversation, user_id))
     → 异步生成 card_title / summary / mood_state，写入 DB（见第十六章）
```

```swift
var coverImageSource: ImageSource {
```

```
                    │
                    └─ Step 4: classify_and_score(transcript, selected_ids)
                                → 单次 Gemini Flash 调用
                                → 同时完成：场景分类 + 每个技能打分（0-100）
                                → 返回 {primary_category, skill_scores{}, other_person_type}
                                    │
                                    └─ _build_stubs_auto(selected_ids, scores, primary_cat)
                                          → 过滤 + 排序 → skill_card stubs
                                              │
                                              └─ _append_always_run(stubs, transcript)
                                                    → 置顶 emotion_recognition
                                                    → 条件追加 depression_prevention
```

### 11.2 核心 LLM 调用：classify_and_score

**文件**：`skills/router.py` 第 222-397 行
**模型**：`gemini-2.5-flash`（复用 GEMINI_FLASH_MODEL 常量）
**调用方式**：同步 `model.generate_content(prompt)`，在 asyncio.to_thread 中运行

**完整 Prompt 结构**：
```
You are an expert conversation analyst specializing in interpersonal dynamics.
Analyze the transcript carefully using the three steps below.

## Step 0: Identify the Other Person
Who is Speaker B? Pick ONE:
  boss_or_superior / coworker_or_peer / subordinate / romantic_partner /
  parent_or_inlaw / child_or_teen / other_family / professor_or_teacher /
  classmate_or_roommate / close_friend / stranger_or_service /
  self_reflection / unknown

## Step 1: Scene Classification → 6大iOS分类
  - "work_life":       Speaker B 是领导/同事/客户/HR
  - "campus_life":     Speaker B 是教授/同学/室友
  - "relationships":   Speaker B 是恋人/朋友
  - "family":          Speaker B 是配偶/父母/子女/亲戚
  - "personal_growth": 无明确 Speaker B，用户自我反思
  - "life_skills":     Speaker B 是房东/医生/客服/邻居

  歧义处理规则（按优先级）：
  1. Speaker B 有职务/职场权力 → work_life（即使话题看起来私人）
  2. Speaker B 是配偶/父母/子女 → family（不用 relationships）
  3. 对朋友倾诉工作/家庭 → relationships
  4. work_life vs personal_growth → 优先 work_life
  5. family vs relationships → 优先 family

## Step 2: Skill Relevance Scoring（0-100）
  为每个 selected_skill_id 打分：
  80-100: 高度相关，用户能立即受益
  50-79:  有一定相关，非核心问题
  0-49:   不相关或边缘相关
  要求：分散打分，避免全堆在50附近

Return ONLY valid JSON:
{
  "other_person_type": "...",
  "primary_category": "...",
  "scene_description": "1-2句话描述发生了什么",
  "skill_scores": { "skill_id": 0-100, ... }
}
```

**关键特性**：
- Step 0 + Step 1 + Step 2 **一次 LLM 调用**完成，不分多次请求
- `selected_skill_ids` 是用户已选偏好技能（来自 `user_skill_preferences` 表）
- 每个技能附带 `name` + `focus`（来自技能配置）送入 prompt 帮助 LLM 理解

### 11.4 过滤与排序规则（_build_stubs_auto）

```
输入：selected_ids（用户偏好） + LLM scores（各技能0-100分）

Step 1：按 iOS 分类分组
Step 2：每个分类取最高子技能分作为"代表分"
Step 3：场景过滤
         代表分占所有分类总分 < 5% → 剔除该场景
         例外：primary_category 强制保留（即使占比<5%）
Step 4：场景排序
         primary_category 置顶，其余按代表分降序
         最多保留 3 个场景
Step 5：子技能过滤
         每个场景内：score ≥ 90 才展示
         每个场景最多3条，按分数降序
         兜底：primary_category 内无90+技能时，展示最高分1条
Step 6：execute_now 标记
         每个场景的第一条技能 execute_now=True（立即执行）
         其余 execute_now=False（按需展示）

输出 stub 格式：
{
  "skill_id": "salary_negotiation",
  "skill_name": "Salary Negotiation",
  "category": "work_life",
  "score": 91,
  "execute_now": True,
  "content_type": "pending",
  "content": None
}
```

### 11.7 chat session 场景下是否需要改现有代码

**结论：match_skills 核心逻辑完全不需要改，只需新增一个包装函数。**

| 现有能力 | chat session 适用性 |
|---|---|
| transcript 只有1条消息时 | ✅ 适用，prompt 支持单条对话分析 |
| profiles=None（无声纹匹配） | ✅ 适用，`_forced_category_from_profiles([])` 返回 None，流程正常 |
| user_id 读偏好 | ✅ 直接复用 |
| 43个技能兜底 | ✅ 直接复用 |
| 关键词快速分类 | ✅ 更快，chat 场景的文本通常关键词明确 |
| score≥90 过滤 | ⚠️ 单条消息信息量少，LLM 打分可能分数偏低；可考虑 chat 模式降低门槛至 **75** |
| execute_now / execute_all | ✅ chat session 只需 skill_tags（标签名），不需要 execute_skill 完整执行 |

**新增的包装函数（在 assistant.py 中）：**

```python
async def _init_skill_matching(
    session_id: str,
    message: str,
    user_id: str,
    sse_queue: asyncio.Queue,         # 匹配完成后推送 skill_tags 事件
    # ⚠️ 不接收 db 参数：本函数由 asyncio.create_task 调用，
    #    handler 返回后 FastAPI 的 db session 已关闭，传入会导致崩溃。
    #    参考 save_kg_from_chat 的模式：内部自建 session。
):
    """
    chat session 第1条消息触发的轻量技能匹配
    - 不执行 execute_skill（不生成策略内容）
    - 只做分类+打分，取 skill_name 列表作为标签推送给客户端
    - 结果写入 strategy_analysis 供后续对话使用
    """
    try:
        # 1. 构造单条 transcript
        transcript = [{"speaker": "user", "text": message, "is_me": True}]

        # 2. 调用现有 match_skills（不改函数本身）
        from database.connection import AsyncSessionLocal
        from skills.router import match_skills
        async with AsyncSessionLocal() as db:   # ← 自建 session，生命周期独立
            stubs = await match_skills(
                scene_result={},
                db=db,
                transcript=transcript,
                user_id=user_id,
            )

            # 3. 提取技能标签名（过滤 emotion_recognition，因为它是常驻技能）
            tag_names = [
                s["skill_name"] for s in stubs
                if s["skill_id"] != "emotion_recognition"
                   and s.get("score") is not None
            ][:3]

            # 4. 写入 strategy_analysis（供后续 /chat 读取 skill_cards）
            # ⚠️ 用 UPSERT 而非 INSERT：iOS 网络重试可能导致本函数被调用两次，
            #    普通 INSERT 在 session_id unique constraint 上会抛异常，
            #    被 except 静默吞掉后技能 context 丢失。UPSERT 直接覆盖，安全。
            from sqlalchemy.dialects.postgresql import insert as pg_insert
            from database.models import StrategyAnalysis
            stmt = pg_insert(StrategyAnalysis).values(
                session_id=uuid.UUID(session_id),
                skill_cards=stubs,
                scene_category=stubs[0].get("category") if stubs else "work_life",
            ).on_conflict_do_update(
                index_elements=["session_id"],
                set_={
                    "skill_cards":    stubs,
                    "scene_category": stubs[0].get("category") if stubs else "work_life",
                }
            )
            await db.execute(stmt)
            await db.commit()

        # 5. 推送 skill_tags SSE 事件（session 已关闭，queue 操作在外面）
        sse_queue.put_nowait(("skill_tags", tag_names))

    except Exception as e:
        logger.warning(f"[chat] 技能匹配失败 session={session_id}: {e}")
        # 失败不影响主对话，静默处理
```

| 对比项 | review session（现有） | chat session（新增） |
|---|---|---|

## 十二、上下文处理机制详细设计

> 代码位置：`server_code/api/assistant.py` + `server_code/services/knowledge_graph.py`

### 12.1 上下文是怎么处理的

**架构：客户端持有历史，服务端无状态。**

每次 `POST /assistant/chat` 请求，客户端把**完整对话历史**带上来：

```json
{
  "session_id": "uuid",
  "skill_id": "emotion_recognition",
  "message": "今天开会被领导批评了",
  "history": [
    { "role": "user",      "content": "我最近压力很大" },
    { "role": "assistant", "content": "我注意到你情绪有些低落..." },
    { "role": "user",      "content": "对，主要是工作问题" },
    { "role": "assistant", "content": "能具体说说吗？" }
  ]
}
```

服务端 `_build_prompt()` 把 history 格式化后拼入 prompt：

```
Conversation history:
User: 我最近压力很大
AI: 我注意到你情绪有些低落...
User: 对，主要是工作问题
AI: 能具体说说吗？
```

**服务端没有任何 session 存储**，每次请求都是一次完整的无状态调用。

### 12.2 记忆是怎么拉取的

每轮对话，服务端都会调用 `get_ai_context_kg(message, user_id, db)`，流程如下：

```
用户消息文本
  │
  ├─ 扫描文本中是否出现 KgPerson 表里已知人名
  │
  ├─ 命中人名 → 返回 top-3 匹配人物的结构化记忆块：
  │     格式示例：
  │     【张三】上司，亲密度6，摩擦度8
  │       事件[2026-05-01] 被当众批评（已解决）
  │       目标[进行中] 争取Q3晋升
  │       技能[2026-05-20] 情绪识别
  │
  ├─ 未命中任何人名 → fallback：返回该用户最近5条事件
  │
  └─ 超时（3秒）→ 静默跳过，memory_context = ""，不阻塞主流程
```

记忆拼入 prompt 的位置：

```
Relevant memory context:
【张三】上司，亲密度6，摩擦度8
  事件[2026-05-01] 被当众批评（outcome: 已解决）
  目标[进行中] 争取Q3晋升
```

**记忆是怎么写进去的（写路径）：**

每轮对话结束后，`save_kg_from_chat()` 异步 fire-and-forget 运行，用 Gemini 从本轮对话中抽取人物/事件/目标，写入 KG 表。下次对话检索时即可命中。

```
对话结束（SSE done 事件推送后）
  → asyncio.create_task(save_kg_from_chat(...))  ← 不阻塞，后台运行
      → Gemini 抽取：人物、事件、目标
      → 写入：kg_persons / kg_events / kg_goals / kg_skills
      → 下次对话 get_ai_context_kg() 即可查到
```

### 12.3 上下文过长时有没有压缩

**有压缩，但只压缩了技能内容，对话历史没有服务端压缩。**

#### 服务端压缩：技能内容按轮次省略

```python
# assistant.py 第106-110行
history_turns = len(history) // 2   # 每轮 = 1条user + 1条AI

if history_turns < 3:
    # 前3轮：完整注入技能的 strategy content（JSON）
    skill_block = f"Work context reference ({skill_name}):\n{skill_content_json}"
else:
    # 3轮之后：技能内容直接省略，只保留技能名
    skill_block = f"Work context reference ({skill_name}): [known skill context, omitted to save tokens]"
```

#### 客户端截断：对话历史最多20条

`AIAssistantViewModel` / `ChatAIAssistantViewModel` 在本地做两道限制：

| 限制 | 值 | 说明 |
|---|---|---|
| 最大消息条数 | 20 条（约10轮对话） | 超过20条，最早的消息从 UserDefaults 中移除 |
| TTL 过期 | 7天 | 7天未使用的历史自动清除 |

**结论：没有 token 级别的动态压缩。** 靠"客户端截断20条 + 技能内容3轮后省略"来控制 prompt 长度。

#### 当前上下文 prompt 的完整结构（按顺序）

```
1. System prompt（固定，约200 tokens）
   └─ "You are the user's workplace AI assistant..."

2. skill_block（前3轮完整，之后省略）
   └─ skill_content_json（策略/情绪卡片内容，约100-300 tokens）

3. conversation_summary（来自 AnalysisResult，约100 tokens）
   └─ "Work conversation summary: ..."

4. memory_context（来自 KG，约50-200 tokens）
   └─ "Relevant memory context: 【张三】..."

5. history_block（最多20条，约200-800 tokens）
   └─ "Conversation history:\nUser:...\nAI:..."

6. task_desc（当前轮任务描述，约100 tokens）
   └─ 根据 message 类型（__INIT__ / __SWITCH__ / 普通）变化

7. suggestions_instruction + meme_instruction（固定，约150 tokens）

总计约：900-1850 tokens per request
```

### 12.4 技能匹配后怎么延续或切换

#### 现有机制（review session）

**技能从进入页面起固定，整个会话不自动变更。**

```
TaskDetailView → 用户点击技能卡"情绪识别"
  → 打开 AIAssistantView(sessionId, skillCard: 情绪识别)
      → 每轮 /chat 请求固定带 skill_id = "emotion_recognition"
          → 服务端始终读同一张技能卡的 content

唯一切换方式：
  用户返回 detail 页 → 点击另一张技能卡 → 发送 message="__SWITCH__" + 新 skill_id
  → 服务端写一段自然过渡语，切换 context
```

**问题**：用户话题漂移时（比如从分手聊到了老板），AI 仍用旧技能 context 回复，质量下降，且用户没有感知。

#### 新方案（chat session）：自动档 + 手动档

**自动档（默认）：并行漂移检测，下一轮生效，零额外延迟**

```
用户发消息
  │
  ├─ [主线，立即] 用当前 skill_id context → Gemini 流式回复
  │               300-500ms 内出第一个字（不等技能匹配）
  │
  └─ [后台并行] 漂移检测（不阻塞主线）
        │
        ├─ Step 1：关键词快速扫描（<1ms）
        │     命中明显新分类（如"老板" → work_life，当前是 relationships）
        │     → 触发 Step 2
        │     未命中 → 结束，保持当前技能
        │
        └─ Step 2：classify_and_score（1-2秒）
              → 新 top 技能 ≠ 当前技能 且 分差 > 15 分
              → 更新 current_skill_id
              → SSE 推送 skill_tags 更新事件
              → 前端技能标签切换动画（静默，不打断对话）
              → 下一轮 /chat 请求用新技能 context
```

**手动档：用户选定技能，关闭后台检测**

```
输入框旁开关切到"手动"
  → 弹出技能选择器（来自用户技能库 user_skill_preferences）
  → 用户选中"职场丛林法则"
  → 当前轮发送 __SWITCH__ + 新 skill_id
  → 服务端：写过渡语 + 切换 context
  → 后续所有轮次固定用该技能
  → 后台漂移检测关闭

用户想再切换：
  → 点输入框开关 → 选新技能 → 重复上述流程
```

**漂移检测触发阈值：**

| 条件 | 说明 |
|---|---|
| 新技能分数 - 当前技能分数 > 15 | 避免小幅波动触发切换 |
| 关键词命中明显新分类 | 快速路径，跳过 LLM |
| 连续2轮均偏向新技能 | 防止单条消息误判（可选，取决于体验调优）|

**为什么不影响当前轮响应速度：**

- 主线流式回复与后台检测**完全并行**
- 用户 300-500ms 内看到第一个字（等同于 Claude/ChatGPT 体验）
- 技能标签更新在 1-2 秒后，用户视觉上感知为"AI 分析完了标签"
- 与豆包等产品的"思考中..."动画效果相似，不影响主流程

### 12.6 App 生命周期处理（强退 / 后台）

> 问题：用户上滑关闭 App 或切到后台，不会触发退出弹窗，`close-chat-session` 不会被调用，session 永远 processing。

#### 两道防线

**防线一：每轮对话后立即持久化（iOS，已有 UserDefaults 机制，确认时机）**

```
用户发消息 → SSE done → AI 回复完整文本拼好
  → 立即写 UserDefaults：
      key: "chat_history_{session_id}"
      value: 完整 conversation 数组（含本轮）
  // 不等到退出时再写，每轮覆盖存一次
  // 强退后重进 App，历史依然可恢复
```

**防线二：App 进入后台时触发 close（iOS，新增）**

```swift
// SceneDelegate.swift 或 AppDelegate.swift
func sceneWillDeactivate(_ scene: UIScene) {
    guard let sessionId = ChatAIAssistantViewModel.shared?.activeSessionId,
          let conversation = ChatAIAssistantViewModel.shared?.conversation,
          !conversation.isEmpty else { return }

    // 用 URLSession background task 保证 App 挂起后仍能发出
    let task = URLSession.shared.dataTask(with: closeRequest(sessionId, conversation))
    task.resume()
    // 给系统约 0.5-1 秒完成这个请求
}
```

> ⚠️ iOS 对 `sceneWillDeactivate` 可用时间约 0.5-1 秒，必须用轻量同步请求或 background URLSession，不能用 async/await。

**防线三：服务端定时清理孤儿 session（兜底）**

```
每小时运行一次（cron 或 startup task）：
UPDATE sessions
  SET status = "archived",
      finalize_status = "failed"   ← 标为失败，iOS 不再轮询
WHERE session_type = "chat"
  AND status = "processing"
  AND created_at < NOW() - INTERVAL '2 hours'
// 超过2小时还是 processing 的 chat session，视为强退孤儿，直接归档
```

#### 三道防线覆盖场景

| 场景 | 防线一 | 防线二 | 防线三 |
|---|---|---|---|
| 正常退出（弹窗选择）| 不需要 | 不需要 | 不需要 |
| 切后台后重新打开 App | ✅ 历史已持久化，可继续对话 | ✅ close 已发出 | - |
| 上滑强退 App | ✅ 历史已持久化 | ✅（sceneWillDeactivate 触发）| 兜底 |
| App crash（强制结束）| ✅ 每轮已写 UserDefaults | ❌ 无法触发 | ✅ 2小时后归档 |

## 十三、技能模式设计（自动档 + 手动档）

> 核心问题：每 query 做技能识别会拖慢响应速度。解法：并行执行，主线不等检测结果。

---

### 13.1 设计原则

- **TTFT（第一个 token 出现时间）不受技能匹配影响**，始终 300-500ms 内出字
- 技能匹配在后台并行跑，结果作用于**下一轮**，不影响当前轮回复
- 自动档大多数轮次只做关键词扫描（<1ms），只有话题漂移时才触发 LLM 调用
- 手动档关闭后台检测，节省资源

---

### 13.2 自动档：并行漂移检测，下一轮生效

```
用户发消息
  │
  ├─ [主线，立即] 用 current_skill_id context → Gemini 流式回复
  │               300-500ms 内出第一个字（不等任何技能判断）
  │
  └─ [后台并行，asyncio.create_task] _detect_skill_drift()
        │
        ├─ Step 1：关键词快速扫描（<1ms，无 LLM）
        │     扫描用户消息是否命中明显新分类：
        │       "老板/领导/KPI" → work_life
        │       "男朋友/分手/失恋" → relationships
        │       "妈妈/爸爸/孩子" → family
        │       ...
        │     ┌─ 命中且与 current_skill 分类不同 → 进入 Step 2
        │     └─ 未命中 → 结束，保持当前技能（本轮最常见路径）
        │
        └─ Step 2：classify_and_score（1-2秒，有 LLM）
              → 仅在关键词命中时触发，非每轮都跑
              → 拿到新 top 技能分数
              → 判断：新技能分数 - current_skill 分数 > 15
                  ├─ 成立 → 更新 current_skill_id
                  │          → SSE 推送 skill_tags 更新事件
                  │          → 前端技能标签切换动画（静默，不打断对话）
                  │          → 下一轮 /chat 请求用新技能 content
                  └─ 不成立 → 保持当前技能（避免小幅波动抖动）
```

**每轮实际开销（自动档）：**

| 场景 | 触发路径 | 额外开销 |
|---|---|---|
| 话题未漂移（大多数轮次）| 关键词未命中 → 结束 | <1ms，几乎 0 |
| 话题轻微变化 | 关键词未命中 → 结束 | <1ms，几乎 0 |
| 话题明显漂移 | 关键词命中 → classify_and_score | 1-2秒后台，不阻塞主线 |

---

### 13.3 手动档：用户指定技能，立即生效

```
用户在输入框旁切到手动档
  → 弹出技能选择器（来自 user_skill_preferences 表）
  → 用户选中"职场丛林法则"
  → 当前轮发送：message="__SWITCH__", skill_id="workplace_jungle"
  → 服务端：
      ├─ 切换 skill_content（读 workplace_jungle 的 strategy content）
      └─ 写一句自然过渡语（"切换到职场技能，..."）
  → 后续所有轮次固定使用该技能
  → 后台漂移检测关闭（skill_mode="manual"，不再触发 _detect_skill_drift）

用户想再切换：
  → 点输入框开关 → 选择新技能 → 发送 __SWITCH__ + 新 skill_id
```

---

### 13.4 模式开关 UI 设计

```
输入框左侧常驻 pill 按钮：

  自动档：  [🔄 情绪识别 ▾]   ← 显示当前自动匹配到的技能名
  手动档：  [🎯 职场丛林 ▾]   ← 显示用户选定的技能名

点击 / 长按 → 弹出选择器（bottom sheet）：

  ┌─────────────────────────────┐
  │  技能模式                    │
  ├─────────────────────────────┤
  │  ⚡ 自动匹配（推荐）          │  ← 当前若是自动档，打勾
  ├─────────────────────────────┤
  │  技能库                      │
  │  ○ 情绪识别                  │
  │  ● 职场丛林法则               │  ← 手动选中态
  │  ○ 亲密关系                  │
  │  ○ 非暴力沟通                │
  │  ...（来自用户 skill 偏好库） │
  └─────────────────────────────┘
```

---

### 13.5 漂移检测两个关键阈值

| 参数 | 值 | 原因 |
|---|---|---|
| 分数差阈值 | > 15 分 | 避免偶发一条消息就触发切换，标签来回抖动 |
| 关键词命中最低数 | 1 条（`work_life`/`family`/`relationships` 等高置信分类）| 快速路径，减少误触发 LLM |
| 连续误判保护 | 可选：连续 2 轮命中新分类才切换 | 防止单条消息误判（初期先不做，视实际效果决定）|

---

### 13.6 切换时是否通知用户

| 切换方式 | 通知形式 | 原因 |
|---|---|---|
| 自动档漂移切换 | 静默 + 技能标签动画 | 不打断对话流，用户感知为"AI 自动调整了" |
| 手动档用户选择 | AI 写一句过渡语（`__SWITCH__`）| 用户主动操作，明确的切换感是好体验 |

### 13.7 涉及改动的模块

| 模块 | 改动内容 | 改动量 |
|---|---|---|
| `api/assistant.py` | 新增 `_detect_skill_drift()` 后台任务；`/chat` 接口新增 `skill_mode` 参数；读 `skill_mode` 决定是否触发漂移检测 | 中 |

| `ChatAIAssistantView.swift` | 输入框左侧 pill 按钮；技能选择器 bottom sheet | 中 |

### 13.9 技能规模扩展说明（未来 340 技能时）

当前并行漂移检测方案在技能数量增长时的演进路径：

```
当前（43技能）：
  关键词扫描 → 命中 → classify_and_score（全量打分）

未来（340技能）—— 只改 _detect_skill_drift 内部：
  Step 1：关键词扫描 → 确定 primary_category（不变）
  Step 2：category 内筛选（约57个技能）→ embedding 相似度检索 → top 20
  Step 3：LLM rerank top 20 → top 3（小 prompt，精准）

外部接口（assistant.py 调用方）完全不变。
```

## 十四、已确认决策记录

| # | 问题 | 决策 |
|---|---|---|
| 1 | **直接退出时 Moment 封面** | 使用用户在 Settings 中选择的 emoji style 情绪头像（self/dog/cat × mood），由 `/emotions/avatar-urls` 接口提供，fallback 到 neutral mood |
| 2 | **技能标签展示时机** | 第1条消息发出后标签区显示"分析中..."加载状态；收到 `skill_tags` SSE 事件后替换为实际技能胶囊；发消息前标签区不显示 |
| 3 | **对话转图片风格来源** | 复用 Moment 顶部图片风格选择器当前选中的风格（`TaskListViewModel.selectedStyleKey`），不单独再让用户选 |
| 4 | **detail 页技能卡点击** | chat session 的技能卡点击 → 跳 `ChatAIAssistantView` 恢复对话（非旧 `AIAssistantView`） |
| 5 | **chat session 技能打分门槛** | 从 score≥90 降至 score≥75（单条消息信息量少，避免全部技能被过滤）|
| 6 | **技能切换模式** | 自动档（默认）：后台并行漂移检测，下一轮生效，TTFT 不受影响；手动档：输入框旁开关 + 技能选择器，发 `__SWITCH__` 立即生效 |
| 7 | **漂移切换阈值** | 新技能分数 - 当前技能分数 > 15 分才触发切换，防止单条消息误判 |
| 8 | **上下文压缩策略** | 暂不做 token 级动态压缩，靠"客户端20条截断 + 3轮后技能内容省略"控制 prompt 长度，后续视实际 token 用量再评估 |
| 9 | **退出时统一后处理** | emotion_recognition / card_title / summary 三件事合并为一次 Gemini 调用（`_async_session_finalize`），在用户退出时（close 或 generate-image 两条路径都触发）异步执行，对话期间不做任何情绪分析 |
| 10 | **低分不强匹配** | `_build_stubs_auto` fallback 加最低分下限：review session fallback floor=60，chat session fallback floor=55；低于下限不强匹配任何技能，仅用普通回复 |
| 11 | **Moment 卡片更新策略** | iOS 回到 Moment 列表页（TaskListView onAppear）时轮询，每 2 秒一次，最多 5 次（10秒）；判断依据：`finalize_status == "completed"`；超时保留日期占位文案 + neutral emoji |
| 12 | **card_title 生成时机** | chat session 的 card_title 不在对话中生成，统一在退出时由 `_async_session_finalize` 生成（与 summary / mood_state 同一次 Gemini 调用），格式与 review session 一致（第一人称日记体英文，25-40 词）|
| 13 | **`_init_skill_matching` 与第2条消息的时序** | 不存在竞态。iOS 在 SSE 流式输出期间锁定输入框，用户无法发第2条消息；SSE done（~2-3秒）时 `_init_skill_matching`（~1-2秒后台并行）已写完 DB。第2条消息到达时 `strategy_analysis` 必然存在。|
| 14 | **用户 0 条消息直接退出** | iOS 侧检测 `conversation.isEmpty`：为空时跳过 ActionSheet，直接 `DELETE /sessions/{id}` 清理孤儿 session，移除本地 TaskItem，Moment 列表不出现。不调 close-chat-session，不触发 finalize，不消耗 token。|
| 15 | **App 强退 / 后台处理** | 三道防线：① 每轮 SSE done 后立即覆写 UserDefaults（历史不丢）；② `sceneWillDeactivate` 时用 background URLSession 发 close-chat-session；③ 服务端定时任务：processing 超过2小时的 chat session 自动归档为 finalize_status="failed"。|
| 16 | **skill_tags SSE 丢失补偿** | iOS 收到 SSE done 后检查 `hasReceivedSkillTags`：若为 false，延迟 500ms 发 `GET /tasks/sessions/{id}/strategy` 补取 skill_cards，提取 skill_name 更新标签区；失败则再等 1s 重试一次，仍失败保留"分析中..."。|
| 17 | **finalize 轮询过滤条件** | 必须用 `finalizeStatus == "pending"`，不能用 `!= "completed"`——后者会把 "failed" 的 session 也纳入轮询，导致每次打开 Moment 列表都无限重试。|
| 18 | **快速连点录音按钮防重复创建** | iOS 侧加 `isCreatingSession` 布尔锁：发出 `init-chat-session` 请求前检查，若为 true 则直接 return；收到响应（成功或失败）后重置为 false。按钮在请求期间置为不可点击状态。服务端无需改动。|
| 19 | **SSE meta `mood_state` 双重用途** | 每轮 SSE meta 里的 `mood_state` 用途：① 驱动对话中的 UI 动效（背景渐变/emoji 动画）；② iOS 覆写 `viewModel.lastMoodState`，退出时作为 Moment 卡片占位 emoji（`lastMoodState ?? "neutral"`），比固定 neutral 更准确。权威值由 `_async_session_finalize` 在退出时基于完整对话生成并写入 DB，轮询完成后替换占位。|
| 20 | **`strategy_analysis` 写入用 UPSERT** | `_init_skill_matching` 写 `strategy_analysis` 时用 `INSERT ... ON CONFLICT (session_id) DO UPDATE SET`（SQLAlchemy `pg_insert().on_conflict_do_update()`）。原因：iOS 网络重试可能导致第1条消息请求重发，进而调用两次 `_init_skill_matching`；普通 INSERT 第二次会触发 unique constraint 报错并被 `except` 静默吞掉，导致技能 context 丢失。UPSERT 直接覆盖，幂等安全。|

## 十五、日志埋点规范

> 以 `session_id` 作为全链路关联 ID。过滤 `[CHAT:{session_id 前8位}]` 可还原单次对话完整链路。
> 关键字段：`turn`（第几轮，从1起）、`elapsed_ms`（耗时）、`skill_id`（当前技能）。

---

### 15.1 日志格式规范

#### 服务端（Python）

```python
# 格式：[CHAT:{session_id 前8位}] {事件描述} | {key=value, ...}
logger.info(f"[CHAT:{session_id[:8]}] session created | user_id={user_id[:8]}")
logger.info(f"[CHAT:{session_id[:8]}] /chat received | turn={turn} msg_len={len(message)} history_len={len(history)}")
```

命名规则：
- `turn` = 第几轮对话（从 1 开始，= len(history)//2 + 1）
- `elapsed_ms` = 该步骤耗时毫秒
- `skill_id` = 当前使用的技能 ID
- `user_id` / `session_id` 仅取前 8 位（隐私保护）

#### iOS（Swift）

```swift
// 格式：[CHAT:{sessionId 前8位}] {事件描述} | {key=value}
```

## 十六、退出时统一后处理（_async_session_finalize）

> **设计原则**：对话期间不做任何情绪分析，退出时一次性完成。三件事（card_title + summary + mood_state）合并为**一次 Gemini 调用**，结果写入 DB，iOS 回到 Moment 列表页后轮询更新卡片。

---

### 16.1 触发时机

| 退出路径 | 触发位置 | 方式 |
|---|---|---|
| **直接退出** | `close-chat-session` 接口返回前 | `asyncio.create_task` |
| **对话转图片** | `generate-image-from-chat` 接口返回前 | `asyncio.create_task`（生图和后处理并行跑）|

两条路径**都触发**，因为 Moment 卡片无论有没有生成图，都需要 card_title 和 emoji。

---

### 16.2 _async_session_finalize 完整数据流

**触发方式**：`asyncio.create_task` — 不阻塞接口响应

```
[服务端] close_chat_session() 或 generate_image_from_chat()
    │
    ├─ Step 1. DB 立即归档（不等后处理）：
    │   UPDATE sessions SET
    │     status          = "archived",
    │     finalize_status = "pending"   ← 新标志位，iOS 据此判断是否需要轮询
    │   WHERE id = session_id
    │
    ├─ Step 2. 触发后处理：
    │   asyncio.create_task(
    │     _async_session_finalize(session_id, conversation, user_id)
    │     # ⚠️ 不传 db：handler 返回后 FastAPI db session 已关闭
    │     #    _async_session_finalize 内部自建 AsyncSessionLocal()
    │   )
    │
    └─ Step 3. 立即返回 200（不等任何 LLM 调用）

[后台] _async_session_finalize(session_id, conversation, user_id)
    # 函数签名不含 db，内部自建 session（同 save_kg_from_chat 模式）
    │
    ├─ 输入：iOS 传来的完整 conversation 数组
    │   [
    │     { "role": "user",      "content": "今天开会被领导当众批评了" },
    │     { "role": "assistant", "content": "我听到你今天承受了很大压力..." },
    │     { "role": "user",      "content": "我当时真的很崩溃" },
    │     { "role": "assistant", "content": "崩溃是正常的反应..." }
    │   ]
    │
    ├─ 单次 Gemini Flash 调用（三合一 prompt）：
    │   → card_title：第一人称日记体英文标题（25-40 词，以"I"开头）
    │   → summary：第一人称日记体英文摘要（50-100 词）
    │   → mood_state：Happy/Excited/Content/Neutral/Anxious/Frustrated/Sad/Angry/Overwhelmed
    │   → emotion_type：workplace_stress/relationship_tension/family_conflict/
    │                   academic_pressure/self_reflection/general_venting
    │   → intensity：1-10
    │
    │   LLM 返回 JSON：
    │   {
    │     "card_title":   "I vented to an AI about being called out by my boss in a meeting — I felt humiliated and wasn't sure how to respond.",
    │     "summary":      "Today I opened up about a difficult moment at work. My boss criticized me publicly in a team meeting, and I found myself feeling both embarrassed and helpless...",
    │     "mood_state":   "Frustrated",
    │     "emotion_type": "workplace_stress",
    │     "intensity":    7
    │   }
    │
    ├─ DB 写入（两张表）：
    │
    │   ① INSERT INTO analysis_results
    │       session_id   = "550e8400-...",
    │       card_title   = "I vented to an AI...",
    │       summary      = "Today I opened up...",
    │       created_at   = now()
    │
    │   ② UPDATE sessions SET
    │       mood_state        = "Frustrated",
    │       emotion_type      = "workplace_stress",
    │       emotion_intensity = 7,
    │       finalize_status   = "completed"    ← iOS 轮询到此值时停止
    │     WHERE id = session_id
    │
    └─ 失败处理：
        UPDATE sessions SET finalize_status = "failed"
        logger.error(f"[CHAT:{session_id[:8]}] finalize failed | error={e}")
        // 失败后 Moment 卡片保留占位文案，不影响主流程

伪代码骨架（关键：自建 db session）：
async def _async_session_finalize(session_id, conversation, user_id):
    from database.connection import AsyncSessionLocal
    try:
        result = await asyncio.to_thread(_call_gemini_finalize, conversation)
        async with AsyncSessionLocal() as db:   # ← 自建，不依赖 handler 的 db
            db.add(AnalysisResult(session_id=..., card_title=..., summary=...))
            await db.execute(UPDATE sessions SET mood_state=..., finalize_status="completed")
            await db.commit()
    except Exception as e:
        async with AsyncSessionLocal() as db:
            await db.execute(UPDATE sessions SET finalize_status="failed")
            await db.commit()
```

### 16.4 Moment 列表页轮询设计

**触发时机**：iOS 用户退出 ChatAIAssistantView，自然回到 Moment 列表页（TaskListView `onAppear`）

```
[iOS] TaskListView onAppear
    │
    ├─ Step 1. GET /api/v1/tasks/sessions（正常列表刷新）
    │           → 返回 sessions 列表，含 finalize_status 字段
    │
    ├─ Step 2. 筛选需要轮询的 session：
    │   let pending = sessions.filter {
    │       $0.sessionType == "chat" && $0.finalizeStatus == "pending"
    │       // ⚠️ 必须用 == "pending"，不能用 != "completed"
    │       //    "failed" 的 session 也满足 != "completed"，会被无限重复轮询
    │   }
    │   // 通常只有刚刚退出的那 1 个 session
    │
    └─ Step 3. 对每个 pending session 启动轮询：
               每 2 秒一次：GET /api/v1/tasks/sessions/{session_id}
               最多 5 次（10 秒超时）

               判断完成条件：
               response.finalize_status == "completed"
               → 停止轮询
               → 更新该 session 的 TaskItem：
                   taskItem.title        = response.card_title   （替换日期占位）
                   taskItem.emotionMood  = response.mood_state    （更新 emoji）
                   taskItem.finalize_status = "completed"
               → Moment 卡片 UI 即时刷新

               超时（5次后仍 pending）：
               → 停止轮询
               → 保留占位文案："6月14日的对话" + neutral emoji
               → 不影响其他功能

服务端 GET /api/v1/tasks/sessions/{id} 新增返回字段：
{
  "session_id":      "550e8400-...",
  "status":          "archived",
  "finalize_status": "completed",      ← 新增
  "card_title":      "I vented to an AI about being called out...",  ← 来自 analysis_results
  "mood_state":      "Frustrated",     ← 新增
  "emotion_type":    "workplace_stress",
  "emotion_intensity": 7
}
```

---

### 16.5 Moment 卡片占位 → 最终显示逻辑

```
finalize_status = "pending"（轮询期间）：
  card_title → 显示 "6月14日的对话"（日期占位，由 iOS 本地生成）
  emoji      → neutral（或 last_sse_mood 粗略值，若有）
  封面图     → emoji 头像（直接退出）/ shimmer（对话转图片，等生图）

finalize_status = "completed"（轮询完成后）：
  card_title → "I vented to an AI about being called out..."
  emoji      → dog_frustrated.png（根据 mood_state + emojiStyle）
  封面图     → 不变（emoji 头像 or 生成图）
```
