# 上下文窗口设计 & 竞品调研

> 整理自 2026-06-08 架构讨论，针对 Chatton 长录音场景（3-5 小时，1000+ turns）

---

## 一、当前架构的核心问题

### 问题根源：`_rewrite_running_context()` 全量输入

```
第 10  turn：Gemini 输入 = 10  × ~50 tokens = 500 tokens
第 100 turn：Gemini 输入 = 100 × ~50 tokens = 5,000 tokens
第 1000 turn：Gemini 输入 = 1000 × ~50 tokens = 50,000 tokens  ← 爆炸
```

额外冗余：代码同时传了所有 turns + 从 turns 提炼的 300-token 摘要 —— 摘要本身就是 turns 的子集，重复发送。

---

## 二、修正后的架构：固定上下文窗口

### 核心原则

**Layer 2 改写 = 增量滚动压缩，而非全量压缩**

```
输入 = (上一次 300-token 摘要) + (最近 20 个 turn)
输出 = 新的 300-token 摘要

输入量恒定：300 + 20×50 = ~1,300 tokens（不随对话长度增长）
```

类比：电视新闻每小时更新「昨日要闻 + 今日新增」，不是播报全年所有新闻。

### 四层上下文总量固定

| Layer | 内容 | Token 量 | 随时间变化？ |
|-------|------|----------|------------|
| Layer 1 | 滑动窗口：最近 8 个 turn | ~400 | 固定（始终 8 条） |
| Layer 2 | **当前** Segment 的 running_context | ~300 | 固定（始终 ≤300） |
| Layer 3A | 人物档案（≤3 人） | ~240 | 固定（人数有上限） |
| Layer 3B | 历史事件（按需检索） | ~120 | 按需，0 或 120 |
| **合计** | | **~940–1,060** | **恒定** |

无论聊了 10 分钟还是 5 小时，Gemini 每次收到的上下文大小不变。

## 三、Segment 隔离：跨场景上下文隔离

### 核心洞察

用户先开会（turn 1–300），再社交（turn 301–1000）。
社交阶段的实时推理 **不应包含** 会议内容。

```
Segment 1（开会）: turn 1–300
  running_context_1 = "讨论Q3目标，刘总提出裁员预算..."
  ↓ 检测到边界（沉默 >2min / 话题切换 / 人员变化）

Segment 2（社交）: turn 301–1000
  running_context_2 = NULL（全新开始）

  实时推理传给 Gemini：
  - Layer 1：turn 993~1000（社交内容）        ✓
  - Layer 2：running_context_2（社交摘要）    ✓  无会议内容
  - Layer 3A：人物档案（跨 Segment 保留）      ✓  人是同一批人
  - Layer 3B：只在用户提及"开会说的"时触发    ✓  按需
```

**Segment 1 的会议内容完全不在 Gemini 视野内。**

### 历史 Segment 的用途

| 时机 | 用途 |
|------|------|
| 会话结束后 | 合并所有 Segment 生成总结卡片 |
| Layer 3B 按需检索 | 用户明确引用之前内容时，从归档 Segment 抽取片段 |
| **实时推理** | **不使用**（完全隔离） |

### m 个 Segment 问题的答案

> "1000 个 turn 时，传给 Gemini 的是 m 个 Segment 的总和，还是 1 个 Segment 对所有 turn 的压缩？"

**都不是。只传当前活跃 Segment 的 running_context（≤300 tokens）。**

## 四、极端场景：5 小时不间断单一话题

整个 5 小时都是一个 Segment（无边界触发），1000 个 turn 的处理：

```
初始：running_context = ""
Turn 10:   compress(turn 1–10,      "")         → v1（300 tokens）
Turn 20:   compress(turn 11–20,     v1_300)     → v2（300 tokens）
Turn 30:   compress(turn 21–30,     v2)         → v3（300 tokens）
...
Turn 1000: compress(turn 981–1000,  v999)       → v1000（300 tokens）

每次 Gemini 输入 = ~1,300 tokens（恒定）
```

**代价**：早期 turn 的细节会随时间淡出（rolling summarization 的信息损耗）。
**可接受**：对"职场生存指导"场景，需要的是当前议题 + 关键决策 + 人物立场，不需要 2 小时前某句话的原话。

## 五、竞品调研

### 5.1 情感陪聊类（Character.AI / Replika）

**核心架构：三层记忆**

```
Hot  热记忆：最近 20 条对话     → 始终在 context（sliding window）
Warm 温记忆：Session 滚动摘要   → 始终在 context（rolling compression）
Cold 冷记忆：长期人物档案       → 向量检索，按需召回
```

**关键技术：结构化记忆提取（Memory Extraction）**

不存原始对话，而是提取结构化事实：
```
原始 turn：
"昨天我妈又催我找对象了，真的很烦，我跟你说..."  → 100 tokens

提取后：
"用户最近在被催婚，感到厌烦"  → 15 tokens
```

信息压缩比可达 **10:1**，且不损失关键事实。

---

### 5.2 编程助手类（Cursor / GitHub Copilot）

**核心架构：RAG + 语义检索**

```
当前文件（全量）        → 始终在 context（局部视野）
相关文件（语义检索）    → 向量 DB 检索，召回 top-k 相关代码
最近编辑历史            → 最近 N 个 diff（sliding window）
用户 query             → 作为查询向量，检索相关 symbol/function
```

整个 repo 被索引成向量，但每次 prompt 只召回与当前问题最相关的 ~5 个文件片段。
**核心原则：用户问什么，就取什么，而不是把所有代码塞进去。**

---

### 5.3 业界通用技术模式

#### 模式 1：RAG over 对话历史

```
每条 turn → 存向量数据库（Pinecone / Weaviate / Chroma）
当前输入  → 语义搜索 → 召回最相关的历史 turn
注入 context = 最近 N 条（sliding）+ 语义相关的历史条目
```

效果：用户提到"上次开会说的预算" → 自动检索到 300 turn 前那条 → 精准注入，不需要全量历史。

#### 模式 2：Salience Scoring（重要性评分）

不是所有 turn 都同等重要：

```
"嗯嗯" / "好的" / "对"          → 信息量 = 0，丢弃
"明天投资人见面，不能迟到"        → 信息量高，永久保留
"Q3 目标是降本 15%"              → 决策类，永久保留
```

高信息量的 turn 即使很老也不被滚动压缩掉。

#### 模式 3：Prompt Caching（KV Cache）

```
System Prompt + 历史上下文前缀 → 缓存 KV（Anthropic / OpenAI 均支持）
只有新的 turn 需要全量计算

效果：延迟从 3s → 0.5s（前缀越长，收益越大）
```

#### 模式 4：模型层创新（了解即可）

| 技术 | 作用 |
|------|------|
| Flash Attention | O(n²) 注意力 → O(n) 内存占用 |
| Ring Attention | 多 GPU 分布式处理超长序列 |
| Mamba/SSM 模型 | 线性复杂度，无 attention 开销 |

> 注：以上是模型训练层面，应用层开发者无法直接使用，了解即可。

## 六、Chatton 当前架构差距 & 补充建议

| 当前缺失 | 补充方案 | 优先级 |
|---------|---------|--------|
| `_rewrite_running_context()` 全量输入 | 改为只取最近 20 turn + 旧摘要（增量滚动压缩） | P0（必须改） |
| Segment 边界检测未实现 | 实现 5 种触发信号，触发时创建新 Segment | P0（必须改） |
| 结构化记忆提取缺失 | Segment 结束时从 running_context 提取人物事实存 Layer 3A | P1 |
| 向量检索历史缺失 | 把 turn 存向量 DB，用当前 turn 语义检索历史 | P2（二期） |
| Salience 过滤缺失 | 滑动窗口从 last N 升级为 last N + high-salience old turns | P2（二期） |
| KV Cache 未使用 | 把 system prompt + 人物档案做 prompt caching | P2（延迟优化） |

### 修正后 `_rewrite_running_context()` 伪代码

```python
RECENT_TURNS_LIMIT = 20  # 只取最近 20 条，不是全部

turns_result = await db.execute(
    select(LiveTurn)
    .where(LiveTurn.segment_id == segment.id)
    .order_by(LiveTurn.turn_index.desc())
    .limit(RECENT_TURNS_LIMIT)           # ← 关键修正
)
turns = list(reversed(turns_result.scalars().all()))  # 恢复时序

turns_text = "\n".join(f"{t.speaker}: {t.text}" for t in turns)
old_ctx = segment.running_context or ""

prompt = f"""
你是对话摘要助手。请将最新对话与已有摘要合并，输出新摘要（≤300字）。

【已有摘要】{old_ctx}

【最新 {len(turns)} 轮对话】
{turns_text}

要求：保留核心议题、关键决策、重要共识，删除闲聊和重复内容。
"""
# Gemini 输入量固定：~300 + 20×50 = ~1,300 tokens（不再爆炸）
```

## 七、总结

Chatton 的分层上下文架构（滑动窗口 + 当前 Segment 滚动压缩 + Segment 隔离）已经是业界标准做法的 **70%**。

**核心结论：**

| 用户直觉 | 专业判断 |
|---------|---------|
| turn 用滑动窗口（最近 10 条） | ✅ 正确，fast path 已经这样做了（8 条） |
| Segment 用增量滚动压缩（非全量） | ✅ 正确，也是必须改的地方 |
| 当前 Segment 不包含历史 Segment 内容 | ✅ 正确，这是 Segment 设计的核心意义 |
| 开会→社交，社交上下文不含会议内容 | ✅ 正确，Segment 边界天然隔离 |
| 跨 Segment 的人物记忆仍然保留 | ✅ 正确，Layer 3A 独立持久化 |
| 总上下文保持固定容量 | ✅ 可实现，约 940–1,060 tokens |

剩下 30% 的补齐路径：
1. **P0**：修正增量滚动压缩 + 实现 Segment 边界检测
2. **P1**：结构化记忆提取（比 raw 摘要精度高、token 少）
3. **P2**：向量检索（按需召回历史，而非全量压入）
