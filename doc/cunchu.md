# 数据存储架构分析

> 最后更新：2026-06-05

---

## 一、数据分布总览

| 存储位置 | 存什么 |
|---|---|
| **PostgreSQL（本机 127.0.0.1:5432）** | 所有结构化业务数据（用户、会话、分析结果、知识图谱等） |
| **Cloudflare R2** | 音频文件（新录音）、AI 生成场景图片、情绪头像 |
| **服务器本地磁盘** | 旧录音音频（迁移 R2 前录制，存在 `sessions.audio_path` 字段中） |

> **重要**：architecture.md 文档中标注的"Aliyun RDS"与实际不符。数据库实际运行在 GCP VM 本机（`127.0.0.1`），与 FastAPI 共用同一台机器。

## 二、数据库全部表（共 15 张）

### 业务核心表（10 张）

| 表名 | 内容 | 每条记录大小 |
|---|---|---|
| `users` | 用户账号、Apple ID、订阅状态/到期时间 | < 1 KB |
| `sessions` | 每次录音任务元信息（含音频 URL / 路径指针） | ~1 KB |
| `analysis_results` | AI 分析结果：对话内容（JSONB）、风险点、转录文本、speaker_mapping | **50–200 KB**（随对话长度变化） |
| `strategy_analysis` | 技能卡片列表、场景图片 URL 列表（JSONB） | 10–50 KB |
| `profiles` | 用户人物档案（姓名、关系、声纹音频 URL） | < 1 KB/条，每用户约 5–15 条 |
| `skills` | 技能库内容（含 Prompt 模板） | 系统静态数据，不随用户增长 |
| `skill_executions` | 每次技能执行日志（耗时、成功/失败） | < 1 KB，每次录音产生 2–5 条 |
| `user_skill_preferences` | 用户在技能页勾选了哪些技能 | 极小，每用户约 10–20 条 |
| `custom_skills` | 用户自定义技能（扩展用，当前未开放） | < 1 KB/条 |
| `verification_codes` | 短信验证码（有过期时间，可定期清理） | 极少 |

### KG（知识图谱 / 用户记忆）表（5 张）

| 表名 | 内容 |
|---|---|
| `kg_persons` | 用户记忆中的人物节点（姓名、关系类型、亲密度、摩擦值、权力关系） |
| `kg_events` | 每次录音提取的事件节点（情绪、结果、日期、关联会话 ID） |
| `kg_event_persons` | 事件 ↔ 人物 多对多关联表 |
| `kg_goals` | 用户目标节点（状态：进行中 / 已完成 / 已放弃） |
| `kg_skills` | 每次对话匹配了哪些技能（关联涉及人物 ID 列表） |

## 三、Cloudflare R2 存储结构

```
R2 Bucket（私有）
├── sessions/{user_id}/{session_id}/original.m4a   ← 原始录音（新录音）
├── sessions/{user_id}/{session_id}/images/{n}.png ← Imagen 生成场景图
└── emotion_avatars/{style}/{category}.png          ← 情绪头像（系统静态资源）
```

**访问方式**：全部通过后端代理接口下发，不暴露 R2 直链：
- 音频：`GET /api/v1/tasks/sessions/{id}/audio-file`（JWT 鉴权）
- 图片：`GET /api/v1/images/{session_id}/{index}`（JWT 鉴权）

**旧录音（迁移前）**：`sessions.audio_path` 字段有值，存在服务器磁盘 `/opt/gemini-audio-service/data/`，约 94 MB。

## 五、架构合理性评估

### 当前（< 1000 DAU）：合理，没问题

**优点：**
- 应用层到数据库零网络延迟（同机通信 < 1 ms）
- 12 MB 数据库全部装进 PostgreSQL 内存缓存，查询极快
- 部署简单，节省成本

**风险：**
- **无自动备份**：服务器宕机或磁盘故障，数据库与应用同时丢失
- **单点故障**：一台机器挂了，全部停服
- RAM 竞争：PostgreSQL 与 FastAPI 共用 3.8 GB，高并发时可能内存紧张

## 六、用户量承载上限

### 存储维度（磁盘）

| 用户量 | 预估 DB 大小 | 磁盘占用 | 结论 |
|---|---|---|---|
| 1,000 活跃用户 | ~500 MB | 无压力 | ✅ |
| 10,000 活跃用户 | ~5 GB | 无压力 | ✅ |
| 50,000 活跃用户 | ~25 GB | 接近上限 | ⚠️ 需扩磁盘或迁 RDS |
| 100,000+ | > 50 GB | 超过磁盘 | ❌ 必须迁 RDS |

（音频和图片已在 R2，不计入磁盘压力）

### 查询性能维度（并发）

| 并发用户数 | 表现 | 说明 |
|---|---|---|
| < 100 并发 | 完全流畅 | 12 MB DB 全在内存 |
| 100–500 并发 | 基本正常 | asyncpg 连接池可能成瓶颈 |
| 500–2000 并发 | 开始抖动 | 建议加 pgBouncer 连接池 |
| 2000+ 并发 | 需迁 RDS | 单机 PostgreSQL 扛不住 |

### 实际瓶颈：Gemini API，不是数据库

- 免费额度：1,500 次/天
- 每次录音 ≈ 6–8 次 Gemini 调用
- **实际上限：~200 DAU**（超过需付费升级 API）
