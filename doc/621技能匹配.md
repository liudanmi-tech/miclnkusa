## 二、完整匹配流程（自动模式）

```
用户对话 transcript
       │
       ▼
Step 1: 读取用户技能偏好
  _get_user_selected_skills(user_id, db)
  → is_manual_mode, selected_skill_ids
  → 若无任何偏好 → 使用全部 43 个系统技能兜底
       │
       ▼
Step 2: 分类预推断（优先级顺序）
  ① _forced_category_from_profiles(profiles)
       档案的 relationship_type → 强制分类
       职场类 → work_life
       家庭类 → family
  ② _guess_category_from_transcript(transcript)
       关键词投票 → 候选分类
       personal_growth 需要 ≥2 个词命中
  ③ 以上均无 → 交由 LLM 决定（forced_cat = None）
       │
       ▼
Step 3: LLM 场景分类 + 技能打分（classify_and_score_groq / classify_and_score）
  输入：transcript + selected_skill_ids
  输出：
    primary_category: 6大分类之一
    scene_description: 1句话场景摘要
    skill_scores: {skill_id: 0-100, ...}
    other_person_type: 对方身份标签
       │
       ▼
Step 4: 合并分类结果
  primary_cat = forced_cat OR scene_result["primary_category"]
  （档案/关键词强制分类 > LLM 分类）
       │
       ▼
Step 5: _build_stubs_auto(selected_ids, scores, primary_cat)
  → 构建要展示的技能卡片列表（含场景过滤 + 分数阈值）
       │
       ▼
Step 6: _append_always_run(stubs, transcript)
  → emotion_recognition 置顶（始终执行）
  → depression_prevention 条件追加
       │
       ▼
返回 skill_card stub 列表
```

## 三、分类预推断详解

### 3.1 档案关系强制覆盖（最高优先级）

```python
_WORKPLACE_REL_TYPES = {
    "领导", "上级", "老板", "直属领导", "总监", "经理", "主管", ...
    "同事", "平级", "同级", "合作方", "客户", "甲方", "下属", "团队成员",
}
_FAMILY_REL_TYPES = {
    "老婆", "妻子", "老公", "丈夫", "爸爸", "父亲", "妈妈", "母亲",
    "儿子", "女儿", "孩子", "兄弟", "姐妹", ..., "家人",
}
```

只要档案 `relationship_type` 命中上述集合之一 → 强制 `work_life` 或 `family`。

### 3.2 关键词兜底推断（无档案时）

扫描全部对话文本，按关键词命中数投票：

| 分类 | 典型关键词 | 最低命中数 |
|---|---|---|
| `work_life` | 老板、领导、KPI、绩效、晋升、加薪、开会... | 1 |
| `family` | 老婆、老公、爸爸、妈妈、儿子、女儿... | 1 |
| `campus_life` | 导师、室友、论文、答辩、考研、GPA... | 1 |
| `relationships` | 男朋友、女朋友、分手、暗恋、出轨、闺蜜... | 1 |
| `life_skills` | 房东、医生、银行、客服、保险、快递... | 1 |
| `personal_growth` | 自信、自卑、内耗、拖延、社恐、迷茫... | **2**（防滥触发） |

命中数最多且达到门槛的分类获胜；若无命中 → 交由 LLM 判断。

> **已知问题**：`personal_growth` 的关键词全为负面词（自卑、内耗等），正向内容（如"和宠物玩很高兴"）无法匹配到任何分类，导致 LLM 接管。

## 四、LLM 分类打分详解

### 4.1 Gemini 版（录音/Live）

- 模型：`gemini-3-flash-preview`
- Prompt 结构：3 步（Step0 识别对方身份 → Step1 场景分类 → Step2 打分）
- 包含详细 disambiguation rules（6条）
- 输出字段：`other_person_type` / `primary_category` / `scene_description` / `skill_scores`

### 4.2 Groq 版（AI 对话，~250ms）

- 模型：`llama-3.1-8b-instant`，`temperature=0`，`max_tokens=512`
- Prompt 为简化版（2步，无 Step0 身份识别）
- `response_format={"type": "json_object"}` 强制 JSON 输出
- `other_person_type` 固定返回 `"unknown"`
- Groq 不可用或调用失败 → 自动 fallback 到 Gemini

### 4.3 LLM 打分规则（prompt 中）

```
80–100: Highly relevant — directly addresses what's happening
50–79:  Somewhat relevant — useful context but not the core issue
0–49:   Tangential or not helpful for this conversation
```

缺失技能分数补 `50`（兜底）。

### 4.4 已知问题

- Groq llama-3.1-8b-instant 是英语模型，接收中文对话 + 英文 prompt，理解质量有限
- `personal_growth` 分类在 prompt 中定义为"internal reflection / no clear other person"，日常正面话题容易被错误归入
- LLM 无 "无需技能" 出口，必须返回一个分类，导致不相关对话也会被强制匹配

## 五、_build_stubs_auto 技能过滤规则

```
阈值常量：
  _SCENE_PCT_THRESHOLD  = 0.05   # 场景占比门槛 5%
  _MAX_SCENES           = 3      # 最多保留场景数
  _SKILL_SCORE_MIN      = 90     # 子技能最低展示分
  _MAX_SKILLS_PER_SCENE = 3      # 每场景最多展示子技能数
```

**过滤步骤：**

1. 按 iOS 分类分组所有 `selected_ids`
2. 计算每个场景的"代表分"= 该场景下最高子技能分
3. **场景过滤**：代表分占所有场景总分比例 < 5% → 丢弃该场景（`primary_category` 强制保留）
4. 按代表分降序排列，`primary_category` 置顶，取前 3 个场景
5. 每个场景内：只保留 `score >= 90` 的子技能，降序取前 3 条
6. **兜底**：若 `primary_category` 内没有 90+ 的技能 → 降级展示该场景最高分 1 条（不管分数）

> **关键问题**：兜底机制导致"和宠物玩很高兴"这类对话，在 LLM 错误归类到 `campus_life` 后，即使所有技能分都低于 90，也会强制展示该场景最高分的 1 个技能（如大学交友），用户会看到不相关的推荐。

## 六、始终运行技能

### emotion_recognition（情绪识别，始终）

- 无条件置顶，`always_run=True`，`execute_now=True`
- 不参与用户技能选择，不受场景分类影响

### depression_prevention（抑郁监控，条件触发）

触发条件（`_should_trigger_depression`）：
1. **危机词**（直接触发，不限文字数量）：
   `"不想活"、"想活了"、"活不下去"、"死了算了"、"想死"、"自杀"`
2. **一般词**（需用户消息字数 ≥ 50）：
   `"搞砸"、"没用"、"失败"、"废物"、"烦"、"焦虑"、"抑郁"、"崩溃"` 等约 30 个词

> 只扫描 `is_me=True` 的用户消息，AI 回复不计入。

## 七、手动模式

用户在技能设置中开启手动模式时：

- 跳过全部场景分类和 LLM 打分
- 直接使用用户勾选的所有技能 `selected_ids`
- 每个 iOS 分类内第一个技能 `execute_now=True`，其余为 `False`
- `score` 字段为 `None`（无分数）

## 十、Bug #1 根因详解：「和家人对话 → 匹配到 campus_life」

### 问题链路

```
用户开始对话（iOS initChatSession）
  → 无 contact_id 字段，服务端不知道"对方是谁"
  → _match_skills_serial 调用 match_skills_v2(profiles=None)  ← 硬编码
  → _forced_category_from_profiles([]) → 返回 None（Step① 完全跳过）
  → _guess_category_from_transcript：对话中无"爸爸/妈妈"等词 → 返回 None（Step② 跳过）
  → classify_and_score_groq：Groq 8B 中文理解弱 → 误判 campus_life
  → _build_stubs_auto：family 技能全低分，campus_life 触发兜底
  → 展示"大学交友"等错误技能
```

### 涉及代码位置

| 位置 | 说明 |
|---|---|
| `api/assistant.py` L754 | `profiles=None` 硬编码 |
| `api/assistant.py` L680 `init_chat_session` | 不接收 `contact_id`，不存档案关联 |
| `api/assistant.py` L205 `AssistantChatRequest` | 无 `contact_id` 字段 |
| iOS `NetworkManager.swift` `initChatSession()` | 发送空 body，不携带档案 ID |

### 修复方向

**方案 A（推荐）：在 `/chat` 请求中携带 `contact_profile_id`**
1. `AssistantChatRequest` 新增 `contact_profile_id: Optional[str] = None`
2. `_match_skills_serial` 收到后查 DB 取 `Profile.relationship_type`，构造 `profiles=[{"relationship_type": rel}]` 传入 `match_skills_v2`
3. iOS `AssistantChatRequest` body 新增 `contact_profile_id` 字段，在用户选了联系人的情况下填入

**方案 B（简化）：`/chat` 每轮从 session 关联的 profile 自动查**
- 需要 `sessions` 表新增 `contact_profile_id` 列
- `init-chat-session` 接收 `contact_profile_id` 并落库
- `_match_skills_serial` 通过 `session_id` 查出 profile

当前最小改动：方案 A，改动 3 个文件（`assistant.py` + iOS `NetworkManager.swift` + `ChatAIAssistantViewModel.swift`）。
