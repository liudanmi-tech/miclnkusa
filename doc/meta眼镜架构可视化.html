5说话人身份识别：双管线 + 三输入
眼镜原始 PCM 音频（同一份数据，分两路处理）
身份识别不插入转录流水线，而是并行运行，互不阻塞
⚡ 管线 A：实时转录（不等身份）
Float32 → Int16 PCM（格式转换）
↓
重采样至 16kHz mono
↓
积累约 100ms chunk → Base64 编码
↓
Gemini Live WebSocket → 转录 + Diarization
↓
返回：{speaker: "Speaker_1", text: "...", is_user: false}
→ 立即驱动快速建议（用角色类型，不等身份）
🔍 管线 B：身份识别（并行，不阻塞）
输入 1：PCM 音频段（声纹比对）
累积 Speaker_X 的 2-3 秒连续音频
→ 与 profiles.voiceprint 余弦相似度比对
→ 速度：<500ms ｜ 准确率：>90%（有声纹时）
输入 2：Gemini 文字（点名规则）
用户说"张总"→ 下一句是 Speaker_X 说的
→ 扫描点名模式，纯规则无 LLM
→ 速度：<100ms ｜ 准确率：95%（有点名时）
输入 3：上下文 LLM 推断
每 10 turn 触发，完整 transcript + 档案摘要
→ LLM 分析说话风格、话题、角色语言
→ 速度：3-8s ｜ 准确率：60-70%（兜底）
🗺️ SpeakerMapping（汇合点，随时间收敛） { Speaker_1: 张总(置信度0.97), Speaker_2: 李明(置信度0.65) }
📈 置信度随时间提升（示例：与张总、李明的对话）
T = 0s
Speaker_1：
未知，仅知角色类型=上级
T = 3s
Speaker_1（点名规则）：
张总（95%）· 用户说了"张总"并得到回应
T = 5s
Speaker_1（声纹确认）：
张总（97%）· 声纹+点名双重确认
T = 30s
Speaker_2（LLM推断）：
李明（65%）· 话题是技术细节，匹配工程师档案
结束后
用户确认弹窗 → 最终写入 live_turns.speaker_profile_id
🎯 可行性边界
场景 可行性 主要依赖
1v1，对方有声纹档案🟢 很高声纹比对，3s 内确认
1v1，对方在档案中但无声纹🟢 高点名规则 + LLM 推断
1v2，两人都在档案中🟡 中需要点名线索才能区分
1v2，两人都不在档案中🔴 低只能推断角色类型
1v3 以上🔴 很低多人对话噪音大
6API 设计
🆕 新增端点（/api/v1/live/）
POST /live/sessions
创建 live session，返回 session_id + SSE URL
POST /live/sessions/{id}/turn ⭐
提交一个对话 turn，后端判断是否触发分析
触发规则：3 turn 满 / 距上次 20s / 10 turn 满
GET /live/sessions/{id}/events（SSE）
iOS 长连接，后端推送：suggestion / analysis_ready / image_ready / ping
POST /live/sessions/{id}/end
结束会话，合并 transcript 写入 analysis_results
POST /live/sessions/{id}/reanalyze
用文字记录重跑完整复盘，复用现有策略生成逻辑

POST /audio/upload
录音文件上传，批次分析，Review Mode 专用
GET /tasks/sessions
历史列表，新增 session_type 字段区分 live/recording
GET /tasks/sessions/{id}/status
轮询分析进度，reanalyze 后复用
POST /tasks/sessions/{id}/strategies
策略生成，classify_scene + match_skills + 图片生成
POST /assistant/chat（SSE）
