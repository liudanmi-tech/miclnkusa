## 一、总体架构

```
用户点击录音按钮
    │
    ▼
POST /assistant/init-chat-session
    → DB 创建 session（session_type="chat"）
    → 返回 session_id
    │
    ▼
iOS 打开 ChatAIAssistantView（全屏）
    │
    ▼
用户发消息 → POST /assistant/chat（SSE 流）
    │
    ├─[主线] 立即生成回复（不等技能匹配）
    └─[后台] 第1条消息触发技能匹配（asyncio.create_task）
```

## 二、进入对话后的完整数据流

### 2.1 第一条消息（turn=0）

```
[iOS] POST /api/v1/assistant/chat
Body:
  session_id:        "550e8400-..."
  skill_id:          "emotion_recognition"   ← 固定初始值，不论用户说什么
  message:           "我想和领导谈薪资"
  history:           []                      ← 空
  is_chat_session:   true
  user_language:     "zh"
```

**服务端主线（立即执行，约 10-25ms 完成准备）：**

```
Step 1. t_request = time.time()

Step 2. asyncio.create_task(_init_skill_matching(...))   ← 后台异步，不阻塞主线
        _sse_skill_queue = asyncio.Queue()               ← 用于主线等待 skill_tags

Step 3. 查 strategy_analysis WHERE session_id=?
        → 0 rows（新会话）
        → skill_name = "Emotion Recognition"
        → skill_content_json = "{}"                      ← 无技能指导，空 JSON

Step 4. KG 记忆检索（asyncio.wait_for, timeout=3s）
        get_ai_context_kg(message, user_id, db)
        → 查 PostgreSQL kg_persons / kg_events 表
        → 返回 memory_context（字符串）或空
        → memory_used = True/False

Step 5. 组装 Prompt（~600-1000 tokens）
        system: "Work context reference (Emotion Recognition): {}"
                + memory_context（若有）
        history: []（空）
        user: "我想和领导谈薪资"

Step 6. t_meta → 推送 SSE: { type:"meta", skill_name:"Emotion Recognition", memory_used:bool }
        [日志] meta_sent | elapsed_ms=10~25ms   ← 我们自己的处理极快

Step 7. _stream_gemini(prompt) → 在独立线程桥接到 asyncio Queue
        模型: gemini-2.5-flash（thinking 模型）
        [日志] first_token | ttft_ms=4000~12000ms   ← 纯 Gemini 延迟，我们无法控制

Step 8. token 事件逐个推送给 iOS

Step 9. [SUGGESTIONS] 解析 → 推送 suggestions 事件（4条）

Step 10. t_done → [日志] stream_done | total_ms=5000~15000ms
         推送 SSE: { type:"done" }

Step 11. 等待 skill_tags，最多 8 秒：
         await asyncio.wait_for(_sse_skill_queue.get(), timeout=8.0)
         → 若后台匹配在 8s 内完成 → 推送 { type:"skill_tags", tags:[...] }
         → 若超时 → warning 日志，丢弃

Step 12. fire-and-forget KG 写入（不阻塞）：
         asyncio.create_task(save_kg_from_chat(...))
         → 提取 persons / events / goals → 写入 kg_* 表
```

### 2.2 后台技能匹配（_init_skill_matching）

**与主线完全并行，asyncio.create_task**

```
入参:
  session_id, message("我想和领导谈薪资"), user_id, sse_queue

Step 1. 构造伪 transcript
        [{"speaker": "user", "text": "我想和领导谈薪资"}]

Step 2. match_skills_v2(transcript, profiles=None, user_id, db, model=None)
    │
    ├─ 读用户技能偏好（user_skill_preferences 表）
    │   → 无偏好 → selected_ids = 全部 43 个系统技能 ID
    │
    ├─ 关键词预处理（_guess_category_from_transcript）
    │   → <1ms，无 LLM，快速推断场景分类
    │
    └─ classify_and_score（asyncio.to_thread → 独立线程）
       模型: gemini-2.5-flash-lite
       耗时: ~1.5-2s（之前 gemini-3-flash-preview 要 16s）

       [Prompt 结构] ~2000 tokens:
         Step 0: 识别对方身份（boss/coworker/parent/...）
         Step 1: 6大场景分类（work_life/campus_life/relationships/
                             family/personal_growth/life_skills）
         Step 2: 对 43 个技能逐个打相关度分 0-100
                 每个技能描述：skill_id + name + exec_context.focus

       [出参 JSON]:
         {
           "other_person_type": "boss_or_superior",
           "primary_category":  "work_life",
           "scene_description": "用户希望与上级谈薪资，不知如何开口",
           "skill_scores": {
             "salary_negotiation": 100,
             "emotion_recognition": 88,
             "assertiveness": 60,
             "difficult_boss": 50,
             ...
           }
         }

Step 3. _build_stubs_auto(selected_ids, scores, primary_cat)
   过滤规则（review 场景用 ≥90，chat 场景同样用 ≥90 内部过滤）：
   → 场景占比 < 5% 的场景剔除
   → 每场景保留分数 ≥ 90 的技能（不足则保留最高分 1 个）
   → 每场景最多 3 个技能，最多 3 个场景
   → emotion_recognition 由 _append_always_run 强制置顶

Step 4. 二次过滤（_init_skill_matching 内）
   stubs = [s for s in stubs if score≥75 or skill_id=="emotion_recognition"]

Step 5. UPSERT strategy_analysis
   skill_cards = stubs（含 exec_context，但 content=None）

Step 6. sse_queue.put({"type":"skill_tags", "tags":[{skill_id, skill_name}...]})
   → 若主线 SSE 仍在等待（8s 窗口内） → iOS 收到 skill_tags 事件
   → 若主线已超时关闭 → 事件丢弃，iOS 启动补偿机制

[当前实测耗时]：2s（远快于 8s 窗口，skill_tags 基本能推送成功）
```

**4 个字段说明：**

| `category` | string | iOS 场景分类，用于技能匹配打分和 UI 分组 |

| 子字段 | 作用 | 用在哪 |

## 十二、技能 Note 系统设计方案（KG-Pointer 架构）

> 状态：设计阶段，未实现。设计时间：2026-06-15。

---

### 12.1 核心思想

**Note ≠ 独立数据仓库，Note = KG 的指针集合 + 基础信息缓存。**

当前 KG 已经存储了用户的事实信息（人物、事件、目标）。如果 Note 也存同样的内容，会造成数据冗余，且同一个人/事件在多个技能的 Note 里各存一份，更新时要多处同步。

解决方案：

```
KG（全局事实数据库）                  技能 Note（轻量指针层）
──────────────────────              ──────────────────────────────
人物: 领导张总                       note:salary_negotiation
  └─ 性格: 强势、数字敏感               └─ baseline_text: "3年后端工程师，25k..."
事件: 绩效面谈被压2个月                 └─ baseline_kg_ids: [uuid_张总]
事件: 拿到华为 offer 32k              └─ dynamic_kg_ids: [uuid_绩效面谈, uuid_offer]
目标: Q3晋升
                                     note:difficult_boss
                                       └─ baseline_kg_ids: [uuid_张总]
                                       └─ dynamic_kg_ids: [uuid_绩效面谈]
```

- **张总的节点只在 KG 里存一份**，两个技能各自用指针引用
- **新信息（新 offer）** → 写入 KG → 自动标记到相关技能的 dynamic_kg_ids
- **跨技能受益**：同一个 KG 节点，被多个技能的 Note 引用

---

### 12.2 两层架构：必现层 vs 容错层

纯指针方案的致命弱点：embedding 相似度检索是概率性的，不保证召回。基础信息如果漏了，这个技能对话就废了。

解决方案：**两层分开处理，保证必现的绝不走检索。**

```
┌─────────────────────────────────────────────────────┐
│ Tier 1：基础 Note（必现，100% 可靠）                 │
│   → 直接存文本内容到 baseline_text 字段             │
│   → 加载时直接 SQL 读取，不经过任何检索              │
│   → 内容由用户确认后写入，AI 不擅自修改             │
├─────────────────────────────────────────────────────┤
│ Tier 2：动态 KG 引用（事件/动态信息，容错）          │
│   → 存 KG 节点 UUID 指针（dynamic_kg_ids）          │
│   → 按 embedding 相似度排序，取 top-5              │
│   → 允许漏几条，影响回复质量但不影响可用性          │
└─────────────────────────────────────────────────────┘
```

**Tier 1 的可靠性来源**：`baseline_text` 是 KG 关键内容的冗余文本缓存，直接存到 `skill_notes` 表里。即使 KG 节点因任何原因查询失败，`baseline_text` 依然在。

---

### 12.3 数据模型

```sql
-- 新增表：skill_notes
CREATE TABLE skill_notes (
    user_id           UUID        NOT NULL,
    skill_id          TEXT        NOT NULL,   -- e.g. "salary_negotiation"

    -- Tier 1: 基础信息（必现层）
    baseline_text     TEXT,                   -- 直接存文本，不是指针
    baseline_complete BOOLEAN     DEFAULT FALSE,  -- false = 初始化问卷未完成
    baseline_kg_ids   UUID[],                 -- 对应 KG 节点 UUID（精确查询，100% 命中）

    -- Tier 2: 动态 KG 引用（容错层）
    dynamic_kg_ids    UUID[],                 -- embedding 检索后写入，允许不完整

    -- 元信息
    user_stage        TEXT,                   -- AI 总结的用户当前阶段，如"准备谈薪中"
    last_updated      TIMESTAMPTZ,
    PRIMARY KEY (user_id, skill_id)
);
```

### 12.5 初始化流程（首次激活某技能）

**核心原则：AI 拉 KG 是为了减少用户输入量，不是为了绕过用户确认。** 基础信息必须经过用户的眼睛确认后才能写入。

```
用户第一次触发"薪资谈判"（baseline_complete = false）：

Step 1. 用技能 embedding 去 KG 检索相关节点
        → 找到：工作经历节点、公司信息节点...

Step 2. 与 baseline_fields 对比，生成「草稿 + 缺口清单」
        已找到: work_years=3年, company=中型互联网
        缺口:   current_salary, target_salary（required=true，必须补充）

Step 3. 推给用户确认草稿 + 问卷补充缺口（合并成一次交互）：
  ┌──────────────────────────────────────────────────────┐
  │ 我整理了一下你的基本情况，请确认是否准确，顺便补充   │
  │ 几个我需要知道的信息：                               │
  │                                                      │
  │ ✓ 工作年限：3年（后端工程师）                        │
  │ ✓ 当前公司：中型互联网，支付方向                     │
  │                                                      │
  │ 请补充：                                             │
  │ · 当前薪资大概是多少？                               │
  │ · 期望谈到多少？                                     │
  │ · 有没有其他 offer 在手？（没有可以不填）            │
  │                                                      │
  │ [已有信息有误可直接告诉我]                           │
  └──────────────────────────────────────────────────────┘

Step 4. 用户回复 → 处理三种情况（见 12.6）

Step 5. 写入路径：
        a. 新信息 → 写 KG（kg_events / kg_persons）
        b. baseline_text ← 组装确认后的所有信息
        c. baseline_kg_ids ← 记录对应 KG 节点的 UUID
        d. baseline_complete = true
        e. 进入正常对话
```

### 12.6 用户回应的三种处理情况

```
情况 1: 确认 + 补充缺口
  用户："对的，薪资25k，目标33k，没有 offer"
  → 直接写入，baseline_complete = true，进入对话

情况 2: 部分纠正
  用户："工作年限不对，我做了5年"
  → 更新 KG 对应节点（work_years=5）
  → 重新生成草稿，再次推给用户确认（只确认一次，不循环）

情况 3: KG 无数据（新用户 / 首次使用某技能）
  → 没有草稿，直接走完整问卷
  → 按 baseline_fields 中 required=true 的字段逐一提问
```

### 12.7 四个核心数据流场景

**场景 A：进入对话，加载上下文**

```
1. SELECT * FROM skill_notes WHERE user_id=X AND skill_id='salary_negotiation'
   → baseline_complete = true → 直接读 baseline_text（必现）

2. SELECT content FROM kg_nodes WHERE id = ANY(baseline_kg_ids)
   → 精确 UUID 查询，100% 命中

3. SELECT content FROM kg_nodes WHERE id = ANY(dynamic_kg_ids)
   ORDER BY relevance_score DESC LIMIT 5
   → 容错，允许漏

4. 注入 Prompt：
   [基础信息（必现）] baseline_text
   [最近相关事件]    dynamic KG top-5
   [对话历史]        本次对话 history
   [用户消息]        当前消息
```

**场景 B：对话中出现新信息**

```
用户说："我刚拿到了华为的 offer"

1. KG 提取器（对话结束后 fire-and-forget）：
   → 新建 KG 节点 {type:"事件", content:"拿到华为offer 32k", timestamp:...}

2. Note 标记器：
   → 判断此事件与 salary_negotiation 高度相关（embedding > 0.7）
   → 追加 uuid 到 dynamic_kg_ids

3. 可选跨技能标记：
   → difficult_boss / assertiveness 也相关 → 同样追加
```

**场景 C：基础信息发生变更**

```
用户说："我已经换工作了，现在月薪30k"

1. AI 识别为 baseline 级别变更（非事件，是基础状态更新）
2. 对话结束后提示用户确认：
   "你提到换工作了，我更新一下你的基本信息：
    当前薪资 30k，现任公司 [用户说的公司]，对吗？"
3. 用户确认 → 更新 KG 节点 + 更新 baseline_text
   （不静默更新基础信息，必须用户确认）
```

**场景 D：跨技能信息共享**

```
对话：向上管理 → 提到"张总上周表扬了我"

1. KG 新建事件节点
2. difficult_boss note → dynamic_kg_ids 追加此节点
3. salary_negotiation note → 也追加（AI 判断对谈薪有帮助）

下次打开薪资谈判对话，自动知道"张总最近表扬了你"这个筹码
```

### 12.8 上下文注入优先级

```
┌────────────────────────────────────────────────────────┐
│ 1. [必现] baseline_text                                 │
│    直接 SQL 读取，不走检索                              │
│    示例：工作年限3年、当前薪资25k、目标33k...           │
├────────────────────────────────────────────────────────┤
│ 2. [高优] baseline_kg_ids 对应 KG 节点                 │
│    精确 UUID 查询，接近必现                             │
│    示例：领导张总（性格强势、数字敏感）                 │
├────────────────────────────────────────────────────────┤
│ 3. [容错] dynamic_kg_ids embedding 排序 top-5          │
│    允许漏，影响质量不影响可用性                         │
│    示例：最近3次相关事件                                │
├────────────────────────────────────────────────────────┤
│ 4. [实时] 本次对话 history + 当前消息                  │
└────────────────────────────────────────────────────────┘
```

Token 预算建议：
- baseline_text：≤200 tokens（用户自己写的，不会太长）
- baseline KG 节点：≤300 tokens（top-3，精确引用）
- dynamic KG 事件：≤300 tokens（top-5，容错）
- 合计背景信息：≤800 tokens，留足对话 history 空间

### 12.10 与现有 KG 系统的关系

| 维度 | KG 系统（现有） | Note 系统（新增） |
|------|----------------|-----------------|
| 数据类型 | 事实：人物、事件、目标 | 指针 + 基础文本缓存 |
| 写入时机 | 每轮对话结束（fire-and-forget） | 用户确认后写入 |
| 读取方式 | embedding 相似度检索 | Tier1: 直接SQL；Tier2: UUID精确查 |
| 跨技能 | 所有技能共享一个 KG | Note 是每技能独立视图 |
| 用户感知 | 透明（后台自动） | 可见（需用户确认基础信息） |

**Note 不替代 KG，Note 是 KG 的「每技能视图」**：KG 存全量事实，Note 决定这个技能应该看哪些事实。

### 12.12 Note 写入时机（三个节点）

Note 的写入分三个明确节点，**不在对话中途写，只在边界时机写**。

#### 节点 1 — 首次技能匹配（baseline 初始化）

```
触发条件：skill_notes.baseline_complete = false
          （该用户从未初始化过这个技能的 Note）

流程：
  1. 用技能 embedding 去全量 KG 检索相关节点
  2. 与 baseline_fields 对比，生成「草稿 + 缺口」
  3. 推给用户确认草稿 + 问卷补充缺口（合并一次交互）
  4. 用户确认 → 写入：
       skill_notes.baseline_text    ← 确认后的文本
       skill_notes.baseline_kg_ids  ← 对应 KG 节点 UUID
       skill_notes.baseline_complete = true

写入对象：skill_notes 表（baseline 层）
写入时机：用户确认后立即写，不等退出
```

#### 节点 2 — 对话中每轮结束（KG 写入，Note 指针暂不更新）

```
触发条件：每轮 SSE done 事件后（已实现，fire-and-forget）

当前行为：save_kg_from_chat() → 提取 persons/events/goals → 写 kg_* 表

Note 指针：本轮不更新，等退出时统一处理
原因：减少写入频率，避免 dynamic_kg_ids 碎片化追加
```

#### 节点 3 — 退出时（dynamic 指针更新 + baseline 变更确认）

```
触发条件：用户关闭对话（close-chat-session 调用时）

Step 1: 拿到本次对话期间新写入 KG 的节点列表
        （可通过 session_id + created_at 过滤）

Step 2: 对每个新 KG 节点，判断是否与当前技能相关
        方法：cosine(node.embedding, skill.exec_context.embedding) > 0.6
        相关 → 追加 UUID 到 skill_notes.dynamic_kg_ids
        不相关 → 跳过（该节点可能被其他技能 Note 标注）

Step 3: 检查是否有 baseline 级别变更
        判断依据：新 KG 节点的 type 字段
          type = "state_change" / "goal" / "person_update" → 可能是 baseline 级别
          type = "event" / "opinion"                       → 一般是 dynamic 级别

        若有 state_change 类节点 → 退出时对话框提示用户确认：
          "本次对话中你提到 [xxx]，要更新你的基础信息吗？
           [确认更新]  [下次再说]"

        用户确认 → 更新 KG 节点 + 同步更新 baseline_text
        用户跳过 → 本次不更新（dynamic_kg_ids 仍标注了该节点，下次用时还能取到）
```

#### 写入时机汇总表

| 节点 | 触发时机 | 写入目标 | 是否需用户确认 |
|------|---------|---------|--------------|
| 首次技能激活 | baseline_complete=false | baseline_text + baseline_kg_ids | ✅ 必须确认 |
| 每轮对话结束 | SSE done（已有） | KG（kg_events 等） | ❌ 透明写入 |
| 退出时 | close-chat-session | dynamic_kg_ids（指针追加） | ❌ 透明写入 |
| 退出时（baseline变更） | 检测到 state_change 节点 | baseline_text | ✅ 弹框确认 |
